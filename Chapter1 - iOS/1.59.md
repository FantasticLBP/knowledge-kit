# 零散知识

1. 为什么线上代码尽量不要使用 NSLog("%@", person)?
    因为NSLog使用%@输出本质上是调用了对象的 description 方法，所以代码中存在大量的 NSLog 的时候。会造成性能问题。 
    解决方案：使用宏定义判断当前代码的运行环境，DEBUG 模式下才输出 NSLog，否则就空实现。
    ```objective-c
    #ifdef DEBUG
    ///一个区分开发和线上环境的Log。NSLog的本质是调用对象方法的 description 方法，所以线上代码使用NSLog会造成性能和安全问题
        #define SafeLog(...) NSLog(__VA_ARGS__)
    #else
        #define SafeLog(...)
    #endif
    ```
2. 如果我们想在某个函数或者方法参数指定参数的类型的话，使用 `id` 编译器不会在编译阶段对其真正的类型做检查，如果我们想指定为一个类的对象或者一个类的子类对象的时候可以使用 `__kindof` 。
   ```Objective-c
    - (void)test:(__kindof UIView *)view
    {
        view.subviews;
    }
   ```
3. 经常在 debug 堆栈里可以看到 **libobjc.A.dylib**，A 代表什么？
核心原因是：A 是**Mach-O 动态库「版本符号」**。
macOS/iOS 系统动态库采用 A/B/C 字母版本命名机制，用来区分不兼容、ABI Breaking Change 的库大版本。也是 NeXTSTEP 延续至今的传统：Foundation、CoreFoundation 等大量系统动态库，全都是 XXX.A.dylib 这种字母版本命名规则。
- libobjc.A.dylib = objc 运行时主版本
- 不带后缀的 libobjc.dylib 只是一个软链接（替身），永远指向当前系统默认生效的最新稳定 A 版本
OC Runtime 底层 ABI（函数调用、内存布局、objc_class 结构体、isa union、引用计数机制）发生破坏性的、不兼容的变更时：
- 苹果不会覆盖旧库，直接创建 libobjc.B.dylib、libobjc.C.dylib
- 新旧版本动态库可以共同存在，并行加载
- 老版本继续加载 A 老版本 libobjc.A.dylib，不会因为系统 Runtime 更新而直接崩溃，完美解决 iOS/MacOS 系统升级时，老 App 向下不兼容奔溃的问题


4. fastpath、slowpath

这是 Apple 内核 /objc 源码专为 CPU 分支预测优化 的编译器分支提示宏，是 Objective-C 底层极致性能优化的核心手段。
- `fastpath`：编译器认为这个条件 极大概率成立
- `slowpath`：编译器认为这个条件 极小概率成立

工作原理：**CPU 分支预测**。
现代 CPU 流水线是顺序预取指令并行执行，一旦分支跳转猜错，整个流水线就要清空重试，性能暴跌。

`fastpath(x)` 告诉 GCC/Clang：x 条件成立的概率极高，编译器会把「条件成立」的代码，放在紧邻的连续内存里，CPU 可以一口气预取、流水线顺畅执行，几乎没有分支惩罚
`slowpath(x)` 告诉 GCC/Clang： x 条件成立的概率极低，编译器会把「异常分支」放到远离主流程的内存，常态下 CPU 完全不会预取这段冷门代码，不干扰主流程性能

本质是：`__builtin_except`，这是 GCC 拓展编译器内置函数，原型为：
```C++
long __builtin_expect(long exp, long expected_value);
```
作用：给 CPU 分支预测提供概率提示，不改变代码逻辑，只改变编译后指令排布，返回值永远等于 exp 本身，100% 不影响程序正常逻辑

```c++
#define fastpath(x) ((typeof(x))__builtin_expect(_safe_cast_to_long(x), ~0l))
#define slowpath(x) ((typeof(x))__builtin_expect(_safe_cast_to_long(x), 0l))
```

我们也可以在业务代码中添加 fastpath、slowpath。
在全局宏定义的地方添加下面的代码：
```c++
#define fastpath(x) (__builtin_expect(!!(x), 1))  // 大概率成立
#define slowpath(x) (__builtin_expect(!!(x), 0))  // 小概率成立
```
什么场景适用？
网络请求回调，99%都是成功的，极少数失败
```objective-c
- (void)requestDataCompletion:(void(^)(NSDictionary *data, NSError *error))completion {
    // 网络请求...
    
    NSDictionary *resultData = ...;
    NSError *error = ...;

    // ✅ 成功是 fastpath（极大概率）
    if (fastpath(!error)) {
        completion(resultData, nil);
    }
    // ❌ 失败是 slowpath（极少发生）
    else {
        completion(nil, error);
    }
}
```
模型解析，大多数情况都是成功的，极少数失败
```objective-c
- (instancetype)initWithDict:(NSDictionary *)dict {
    if (slowpath(!dict)) { // 字典为空 = 小概率
        return nil;
    }
    
    if (fastpath(dict[@"name"])) { // 有名字 = 大概率
        _name = dict[@"name"];
    }
    
    // ...
}
```
列表缓存，99% 能命中缓存
```objective-c
- (id)cacheForKey:(NSString *)key {
    if (fastpath(self.cacheDict[key])) {
        return self.cacheDict[key]; // 🔥 最快路径
    }
    
    return nil; // 慢路径
}
```

原则：
1. 永远先写 fastpath 正常逻辑，后写 slowpath 异常逻辑
2. 只在高频调用函数里用，比如：点击事件、页面生命周期、列表复用、网络回调这些高频函数收益极大，冷门一次性逻辑（弹窗消失、页面销毁）加了几乎没效果
