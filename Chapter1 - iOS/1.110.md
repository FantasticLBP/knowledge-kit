## 妙用设计模式来设计一个客户端校验器


> 业务逻辑千变万化，弹窗优先级不断改变，代码冗余问题和难以维护问题如何解决？
> 本篇文章从设计模式角度出发，讨论责任链设计模式和工厂设计模式2个方式，如何去设计一个校验器，同时解决代码冗余和难以维护的问题


## 一、问题背景

订单在提交的时候会面临不同的校验规则，不同的校验规则会有不同的处理。假设这个处理就是弹窗。
有的时候会命中规则1，则弹窗1，有的时候同时命中规则1、2、3，但由于存在规则的优先级，则会处理优先级最高的弹窗1。

老的业务背景下，弹窗优先级或者说校验规则是统一的，且弹窗判断规则不多，直接用函数翻译实现，写多个 if 问题不大。
但随着业务迭代，弹窗规则越来越多，之前维护的人可能偷懒直接修改。且在新业务背景下，不同的条件，弹窗优先级不一致，之前的写法需要写大量的嵌套判断，代码难以维护。

另外，通过 return 顺序决定弹窗优先级，确实能够快速实现需求。但这种写法存在一个**隐性问题**：**弹窗优先级完全由代码书写顺序决定，属于隐含逻辑，不直观、不易读、也不易维护**。

虽然在单一优先级场景下问题不够明显，但一旦进入复杂业务环境 —— 例如不同用户身份（VIP / 非 VIP）、不同账户状态（付费 / 未付费）需要**多套优先级策略**时，if/else 写法会立刻暴露出致命缺陷：嵌套层级急剧加深、大量重复判断、规则冗余、修改成本极高、极易改错。

更为重要的是，if/else 将**校验逻辑、执行顺序、业务场景、弹窗处理**全部耦合在一个函数内，违背单一职责原则；同时优先级写死在代码中，无法灵活调整，更不支持未来动态配置、动态下发等扩展性需求。

因此，我们需要一种更优的模式，把**隐含的优先级变为显式的执行流程**，把**耦合的逻辑拆分为独立可复用的模块**，把**写死的顺序变为可编排、可配置、可动态调整的结构**。

所以问题抽象为：**面对不同的校验规则，如何设计一个校验器**


为了清晰说明问题，假设线上的弹窗校验规则为：A -> B -> C 

```objective-c
typedef NS_ENUM(NSUInteger, OrderSubmitReminderType) {
    OrderSubmitReminderTypeNormal = 0,    // 没有命中校验规则
    OrderSubmitReminderTypeA,             // 命中校验规则 A
    OrderSubmitReminderTypeB,             // 命中校验规则 B
    OrderSubmitReminderTypeC,             // 命中校验规则 C
}
```

老规则比较简单，不存在不同的校验规则，所以需求可以直接用代码翻译，不需要额外设计

```objective-c
+ (OrderSubmitReminderType)acquireOrderValidateType:(id)params {
    if ([OrderSubmitUtils validateA:params]) {
        return OrderSubmitReminderTypeA;
    }
    if ([OrderSubmitUtils validateB:params]) {
        return OrderSubmitReminderTypeB;
    }
    if ([OrderSubmitUtils validateC:params]) {
        return OrderSubmitReminderTypeC;
    }
    return OrderSubmitReminderTypeNormal;
}
```

假设只有2个弹窗条件：是否是 VIP 账户（isVIP）、是否是付费用户（isChargedAccount）。

- `isVIP & isChargedAccount`： A -> B -> C
- `isVIP & !isChargedAccount`：B -> C -> A
- `!isVIP`: C -> B -> A

如果直接改，代码就是一坨垃圾了

```objective-c
+ (OrderSubmitReminderType)acquireOrderValidateType:(id)params {
    if (isVIP) {
       if (isChargedAccount) {
            if ([OrderSubmitUtils validateA:params]) {
                return OrderSubmitReminderTypeA;
            }
            if ([OrderSubmitUtils validateB:params]) {
                return OrderSubmitReminderTypeB;
            }
            if ([OrderSubmitUtils validateC:params]) {
                return OrderSubmitReminderTypeC;
            }
            return OrderSubmitReminderTypeNormal;
       } else {
            if ([OrderSubmitUtils validateB:params]) {
                return OrderSubmitReminderTypeB;
            }
            if ([OrderSubmitUtils validateC:params]) {
                return OrderSubmitReminderTypeC;
            }
            if ([OrderSubmitUtils validateA:params]) {
                return OrderSubmitReminderTypeA;
            }
            return OrderSubmitReminderTypeNormal;
       } 
    } else {
            if ([OrderSubmitUtils validateC:params]) {
                return OrderSubmitReminderTypeC;
            }
             if ([OrderSubmitUtils validateB:params]) {
                return OrderSubmitReminderTypeB;
            }
            if ([OrderSubmitUtils validateA:params]) {
                return OrderSubmitReminderTypeA;
            }
            return OrderSubmitReminderTypeNormal;
    }
}
```

其实不然，问题还是很多：

- 虽然抽取为不同方法，但是每个方法内部存在大量冗余代码，因为每个校验规则的代码是一样的，重复存在，只不过先后顺序不同

## 三、方案设计

### 1. 头脑风暴

那能不能优化呢？软件工程、架构设计中一个很常见的做法是：分层、设计不同角色各个角色各司其职，对应的有几个设计模式可供选择。有3个思路：责任链设计模式、工厂设计模式、策略模式

可能有些人会问：这些模式都会增加类的个数，每个规则对应一个子类，规则增多时类数量快速上升，会不会影响包体积和执行时间？

if 结构：

```shell
if (A) → 不命中
else if (B) → 不命中
else if (C) → 不命中
...
最后走到 Z
```

责任链结构：

```shell
A → 不命中
B → 不命中
C → 不命中
...
最后走到 Z
```

两者执行次数完全相同，时间复杂度完全一样：O (n)



**类膨胀是责任链模式**预期内、可接受、高 ROI 的合理代价。

为什么类膨胀 ROI 极高？

1. **单一职责 → 易读、易测、易改、易删**：一个类只做一件事，改坏概率极低。

2. **完全符合开闭原则**。加规则 = 加类，不动旧代码。

3. **可配置、可组合、可动态编排**。支持后台下发、动态排序、动态开关。

   

### 2. 策略模式

策略模式：当需要根据客户端的条件选择算法、策略时，可用该模式，客户端会根据条件选择合适的算法或策略，并将其传递给使用它的对象。典型设计前端 Vue-Validator form 各种 rules。不知道多少人写过前端，不同规则配置不同 rules，然后在使用的地方，比如 form 表单，配置不同的 rule。

下面来举个 Vue-Validator 的例子：

1. 框架内置 rule：

   ```json
   rules: {
     // 策略1：必填校验
     name: [
       { required: true, message: '请输入姓名', trigger: 'blur' }
     ],
   
     // 策略2：长度策略
     password: [
       { min: 6, max: 16, message: '长度在 6 到 16 个字符', trigger: 'blur' }
     ],
   
     // 策略3：正则策略（手机号）
     phone: [
       { pattern: /^1[3-9]\d{9}$/, message: '手机号格式错误', trigger: 'change' }
     ],
   
     // 策略4：邮箱策略
     email: [
       { type: 'email', message: '请输入正确的邮箱', trigger: 'change' }
     ]
   }
   ```

2. 自定义 rule：

   ```js
   // 自定义策略：校验两次密码一致
   const validatePasswordSame = (rule, value, callback) => {
     if (value !== this.form.confirmPass) {
       callback(new Error('两次输入密码不一致'))
     } else {
       callback()
     }
   }
   ```

3. 使用

   ```js
   rules: {
     confirmPass: [
       { validator: validatePasswordSame, trigger: 'blur' } // 策略注入
     ],
     remark: [
       { validator: validateVIP, trigger: 'change' } // 动态策略
     ]
   }
   ```

4. 前端组件使用

   ```vue
   <el-form :rules="{ phone: phoneRules }">
   ```

不过目前来看，策略模式被 Pass 了



### 3. 责任链设计模式

#### 1. 思路

责任链模式即 Chain Of Responsibility，属于行为型模式。行为型模式不仅描述对象或类的模式，还描述他们之间的通信模式，比如对操作的处理该如何传递等等。当需要根据请求的内容选择处理器时，可用该模式，请求会沿着链传递，直到被处理。

为什么会有这个思路？

主要来源于3个方向：典型的设计有 Node 的洋葱模式、移动端的点击事件传递、大前端的 Vuex、Redux、Fish Redux：

- Node 洋葱模式：发送一个 Request 一层层中间件去处理，比如添加日志、添加请求拦截转发、处理核心业务逻辑、添加日志、添加自定义 response header等，一个中间件层只关注聚焦自己层需要做的事情，处理完继续向下一层抛
- 移动端的事件响应模型：点击 view 看看能不能响应，不能响应则继续向上抛，直到抛到 window 为止；前端 JS 事件冒泡机制：点击事件假设是动态绑定到 DOM 节点上的，浏览器本身不知道哪些地方会处理点击事件，但又要让每层 DOM 拥有对该点击事件的平等处理权，所以就诞生了事件冒泡和组织冒泡的能力 `event.stopPropagation()` 
- 再或者 Vuex、Redux 中的 middlewares 就是标准的「责任链 + 策略模式」混合体，每个 middleware 是一个责任节点，action 沿着 middleware 链条依次传递，每个节点可以：处理、转发、中断。


设想下如果没有中间价模型，假设实现一个记录请求事件和自定义 HTTP Header 的需求，业务逻辑 curd 代码和记录请求时间和自定义 Header 代码全都杂糅在一起，难以维护。

责任链的核心就是：**使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止。**

- 降低处理者对象之间的耦合度。一个对象无须知道到底是哪一个对象处理其请求以及链的结构，发送者和接收者也无须拥有对方的明确信息。
- 增强了系统的可扩展性。可以根据业务需求增加或者调整新的请求处理类，满足开闭原则（类似维护链表的节点信息）
- 可插拔，增强了给对象指派职责的灵活性。当工作流程发生变化，可以动态地改变链内的成员或者调动它们的次序，也可动态地新增或者删除责任。
- 责任链简化了对象之间的连接。每个对象只需保持一个指向其后继者的引用，不需保持其他所有处理者的引用，这避免了使用众多的 if 或者 if···else 语句。
- 责任分担。每个类只需要处理自己该处理的工作，不该处理的传递给下一个对象完成，明确各类的责任范围，符合类的单一职责原则。



#### 2. 角色设计

##### 1. 声明接口

采用责任链设计模式。基类 `OrderSubmitBaseValidator` 声明接口，是一个抽象类：

- 有一个属性 `nextValidator` 用于指向下一个校验器
- 有一个方法 `- (void)validate:(id)params;` 用于处理校验，内部利用模版模式，默认实现是传递给下一个校验器

```objective-c
//.h
OrderSubmitBaseValidator {
    @property nextValidator;
    
    - (void)validate:(id)params;
    - (BOOL)isValidate:(id)params;
    - (void)handleWhenCapture;
}


// .m
#pragma mark - public Method
- (BOOL)isValidate:(id)params {
    Assert(0, @"must override by subclass");
    return NO;
}
- (void)validate:(id)params {
    BOOL isValid = [self isValidate:params];
    if (isValid) {
        [self.nextValidator validate:params];
    } else {
       [self handleWhenCapture];
    }
}

- (void)handleWhenCapture {
    Assert(0, @"must override by subclass");
}
```

##### 2. 子类重写

然后针对不同的校验规则声明不同的子类，继承自 `OrderSubmitBaseValidator`。根据A、B、C 3个校验规则，有：OrderSubmitAValidator、OrderSubmitBValidator、OrderSubmitCValidator。

子类去重写父类方法

```objective-c
OrderSubmitAValidator {
    - (BOOL)isValidate:(id)params  {
        // 处理是否满足校验规则A
    }
    
    - (void)handleWhenCapture {
        // 当不满足条件规则的时候的处理逻辑
        displayDialogA();
    }
}
```

##### 3. 兜底处理

为了设计的健壮，假设没有命中任何校验规则，需要如何处理？这个能力需要有兜底默认的行为，比如打印日志：`NSLog(@"暂无命中任何弹窗类型，参数为：%@"，params);` 也可以由业务方传递

```objective-c
OrderSubmitDefaultValidator *defaultValidator = [OrderSubmitDefaultValidator validateWithBloock:^ {
    SafeBlock(self.deafaultHandler, params);
    if (!self.deafaultHandler) {
        NSLog(@"暂无命中任何弹窗类型，参数为：%@"，params);
    }
}];
```

##### 4. 工厂模式初始化校验规则

封装链构建器，降低组装成本

初始化多个校验规则

```objective-c
OrderSubmitAValidator *aValidator = [[OrderSubmitAValidator alloc] initWithParams:params];
OrderSubmitBValidator *bValidator = [[OrderSubmitBValidator alloc] initWithParams:params];
OrderSubmitCValidator *cValidator = [[OrderSubmitCValidator alloc] initWithParams:params];
```

不同优先级的校验如何指定：

```objective-c
if (isVIP) {
    if (isChargedAccount) {
        aValidator.nextValidator = bValidator;
        bValidator.nextValidator = cValidator;
    } else {
        bValidator.nextValidator = cValidator;
        cValidator.nextValidator = aValidator;
    }
} else {
    cValidator.nextValidator = bValidator;
    bValidator.nextValidator = aValidator;
}
```

**利用策略模式 `validateWith` 方法内部根据 validateType  去组装 Map 的 key，然后从 Map 中取出具体规则组合，然后依次迭代遍历执行**

```objective-c
// ValidateStrategyFactory.m
// 根据业务参数，生成对应的校验策略链
+ (OrderSubmitBaseValidator *)buildChainWithParams:(id)params {
    // 1. 解析业务条件
    BOOL isVIP = [params[@"isVIP"] boolValue];
    BOOL isCharged = [params[@"isChargedAccount"] boolValue];
    // 2. 配置化优先级映射（新增条件/规则只需修改此映射）
    NSDictionary *priorityMap = @{
        @"VIP+Charged": @[@"A", @"B", @"C"],
        @"VIP+UnCharged": @[@"B", @"C", @"A"],
        @"NonVIP": @[@"C", @"B", @"A"]
    };
    // 3. 自动创建并串联节点
    NSString *key = isVIP ? (isCharged ? @"VIP+Charged" : @"VIP+UnCharged") : @"NonVIP";
    NSArray *validatorTypes = priorityMap[key];
    OrderSubmitBaseValidator *head = nil, *prev = nil;
    for (NSString *type in validatorTypes) {
        OrderSubmitBaseValidator *validator = [self createValidator:type params:params];
        head = head ?: validator;
        if (prev) prev.nextValidator = validator;
        prev = validator;
    }
    // 4. 自动接入兜底节点（避免遗漏）
    prev.nextValidator = [OrderSubmitDefaultValidator new];
    return head;
}
```
这部分策略的生成也可以单独抽取出去，比如 ValidateStrategyFactory 去根据不同的信息，生成不同的策略。

##### 5. 使用

朴素实现：

```objective-c
OrderSubmitBaseValidator *validateType = [OrderSubmitValidator generateTypeWithParams:params];
[OrderSubmitValidator validateWith:validateType];
```

但还是不够优雅，这个优先级需要用户感知。需要做到业务方只传递参数，内部判断命中什么弹窗优先级组合。所以接口可以设计为：

```objective-c
[OrderSubmitValidator validateWithParams:params handleWhenNotCapture:^{
    NSLog(@"暂无命中任何弹窗类型，参数为：%@"，params);
}];
```

#### 3. 优点

1. 解决了现在的错误弹窗的隐含逻辑，后续人接手，弹窗优先级清晰可见，提高可维护性，减少出错概率
2. 对于判断（校验）的增减都无需关心其他的校验规则。类似维护链表，仅在一开始指定即可，符合“开闭原则”
3. 对于现有校验规则的修改足够收口，每个规则都有自己的 validator 和 validate 方法
4. 目前弹窗优先级针对 isVIP、isCharged 存在不同优先级顺序，如果按照现有的方案实施，则会存在很多冗余代码
5. 按照策略模式，不同的校验规则，组装不同的策略，也可以单独抽取出去，独立维护，更清晰
6. validate 内部按照模版模式，调用 `isValidate` 方法，每个单独的 Validator 不需要额外去调用 next，设计更加健壮，防止别人漏写



### 4. 工厂设计模式

#### 1. 角色设计

##### 1. 设计基类

```Shell
OrderSubmitBaseValidator {
    - (void)validate;
    
    - (BOOL)validateA;
    - (BOOL)validateB;
    - (BOOL)validateC;
}

- (void)validate {
    Assert(0, @"must override by subclass");
}

- (BOOL)validateA {
    // 判断是否命中规则 A
}
- (BOOL)validateB {
    // 判断是否命中规则 B
}

- (BOOL)validateC {
    // 判断是否命中规则 C
}
```

##### 2. 子类实现

根据不同的弹窗优先级条件，声明3个不同的子类：`OrderSubmitAValidator`、`OrderSubmitBValidator`、`OrderSubmitCValidator`。各自重写  `validate` 方法

```Shell
OrderSubmitAValidator {
    - (void)validate {
        [self validateA];
        [self validateB];
        [self validateC];
    }
}

OrderSubmitBValidator {
    - (void)validate {
        [self validateB];
        [self validateC];
        [self validateA];
    }
}

OrderSubmitCValidator {
    - (void)validate {
        [self validateC];
        [self validateB];
        [self validateA];
    }
}
```

##### 3. 工厂初始化

设计工厂类`OrderSumitValidatorFactory`，提供工厂初始化方法

```Shell
OrderSumitValidatorFactory {
    + (OrderSubmitBaseValidator *)generateValidatorWithParams:(id)params;
}

+ (OrderSubmitBaseValidator *)generateValidatorWithParams:(id)params {
    if (isVIP) {
        if (isChargedAccount) {
            return [[OrderSubmitAValidator alloc] initWithParams:params];
        } else {
            return [[OrderSubmitBValidator alloc] initWithParams:params];
        }
    } else {
           return [[OrderSubmitCValidator alloc] initWithParams:params];
    }
}
```

#### 2. 优点

- 没有重复逻辑，判断方法都守口在基类中
- 优先级的关系维护在不同的子类中，各司其职，独立维护


### 3. 怎么选？
再来回顾下：
- 责任链模式：抽象校验基类，每个校验规则（A/B/C）封装为独立子类，通过 nextValidator 串联成链，请求沿链传递直到命中规则；通过策略 / 工厂管理不同条件下的链组装逻辑。
- 工厂模式：基类收口校验逻辑，子类重写 validate 方法控制优先级顺序，工厂根据业务条件返回对应子类实例。

最后，怎么选？
- 不选工厂模式（因为它用了继承，子类膨胀、难维护、违反开闭）
- 选责任链模式（因为它用组合 / 链式，可插拔、可排序、可动态组装）
**组合优于继承，个人倾向使用责任链模式去组织代码**。关于责任链设计模式的文章也可以看这篇[文章](https://raw.githubusercontent.com/FantasticLBP/knowledge-kit/master/Chapter6%20-%20Design%20Pattern/6.23.md)



## 四、拓展

如果业务真的是高频迭代变化，但校验顺序不变的话，甚至可以做成多端协定后，对应业务校验编号和业务关联，动态下发

```json
// Version1
{
	"validatorRuleOrder": ["1", "4", "3", "2"]
}

// Version2
{
	"validatorRuleOrder": ["1", "3", "4", "2"]
}
```

App 动态请求，然后执行业务逻辑。需思考一些问题：
- 网络请求慢怎么处理？
- 需不需要缓存？
- 有缓存的话，更新策略是什么？
- 需不需要内置的产品逻辑？

站在常见系统设计角度回答下这个问题，不同公司、不同业务要求可能会有不一样的要求。仅供参考

常见设计是：**本地内置兜底 + 远程配置下发 + 多级缓存 + 异步预加载 + 降级策略**



### 1. 网络慢怎么处理

异步加载，不影响主流程

- 不阻塞业务流程：提交订单时**不等网络请求**，直接用**缓存 / 内置规则**
- 后台预加载：App 启动时、切后台时、进入订单页时，**后台悄悄拉取**
- 超时保护：请求超过 300ms～500ms 自动放弃，走缓存
- 并行请求：和其他接口一起发，不单独等待

网络慢：不用等，直接用缓存 / 内置规则，后台慢慢更新。

### 2. 需不需要缓存？

需要，而且是多级缓存。

- 内存缓存：

- 本地缓存：

- App 内置默认规则（兜底）

  

### 3. 更新策略

时机策略

- App 启动时拉取
- 进入订单提交页面时拉取
- 下拉刷新时拉取
- 定时（每 4 小时 / 每 24 小时）拉取

版本策略

- 后台返回 **version/timestamp**
- 本地版本 < 远程才更新

增量更新

- 只下发变化的规则，不下发全量
- 减少体积、加快速度

冲突策略

- **远程规则优先**
- 本地缓存次之
- 内置规则兜底

强制更新

- 重大规则变更，加个 `forceUpdate` 字段
- 必须拉取成功才能进入页面

### 4. 降级策略

- 网络失败：用缓存
- 缓存失效：用内置规则
- 解析失败：用内置规则
- 后端异常：用内置规则



## 五、回顾

本文通过一个具体的业务场景问题，应该是一个典型的问题，并没有引入新的技术，而是通过一个设计模式去解决了问题。责任链模式正是为解决这类问题而生：**它让每个校验规则独立封装、职责单一，通过链式结构明确表达优先级，支持多场景自由编排，并且天然具备可扩展、可配置、可动态化的能力，使整个校验系统从 “能实现” 升级为 “可维护、可管理、可演进”**
